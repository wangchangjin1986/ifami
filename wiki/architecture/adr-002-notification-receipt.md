# ADR-002：触达确认回执制——微信没有"已读"

## 决策

强触达的确认机制是**点击回执制**：触达消息带小程序跳转，用户点开即回执。不存在"已读"状态。

## 背景

微信服务号模板消息、小程序订阅消息都**没有已读回执**。需求层面写的"15 分钟未读→短信"在技术上实现不了，只能实现"15 分钟无回执→升级"。

## 升级链路（状态机）

```
notify_job(level=strong) 生成
  → 通道1 小程序订阅消息（带小程序跳转页）
  → 用户点开 = 回执（前端上报 → 更新 job 状态 → 取消后续）
  → 15min 无回执 → 通道2 应用内待办红点
  → 30min 无回执 → 通道3 备份联系人（配偶）的订阅消息
```

- Phase 0 计时实现：Worker 轮询 `notify_jobs.next_check_at`（30s 粒度）。Phase 1 换 MQ 延迟消息。
- 通道适配层抽象 `Channel` 接口（wechat_template / wechat_subscribe / sms / app_push）。**Phase 0 纯个人主体只实现 `wechat_subscribe`**，`wechat_template` / `sms` 留空实现——升个体户后补齐即恢复，结构零改动。
- 角色默认路由：祖辈 strong=[订阅消息]；可在成员设置覆盖。短信兜底升个体户后追加。

## 关键推论

1. 强触达消息**必须**带跳转链接，且跳转落地页必须上报回执——漏掉上报 = 回执率永远为 0 = 无限升级。
2. **订阅消息额度是真瓶颈**：一次性订阅「一次授权 = 一条额度」，发一条消耗一条。notify 模块内置额度计数与令牌桶；产品上必须把订阅引导前置到录入动作里（录日程/打卡时弹 `wx.requestSubscribeMessage`），否则到期无额度可发。
3. 免打扰时段（默认 22:00–7:00）仅放行 strong。
4. 触达看板是 P0：分通道/分级别的发送成功率、回执率、升级率、端到端时延。

## 纯个人主体的降级与恢复点

- Phase 0（纯个人主体）：通道1 = 小程序一次性订阅消息，通道2 = 应用内待办红点，通道3 = 配偶订阅消息；**无短信**，「强触达」语义被削弱。
- 一次性订阅需用户每次授权，到达率天然低于服务号模板消息——「订阅消息真实到达率/回执率」本身就是 Phase 0 在验假设。
- 升个体工商户后恢复：通道1 换回服务号模板消息（类目模板），通道2 恢复短信，`Channel` 接口只需补 `wechat_template` / `sms` 两个实现。
