# 需求变更：家人加入功能去社交化（加入码 + 当面扫码）

> 变更日期：2026-11-20 · 状态：**设计已确认，进入实现** · 触发：微信个人主体审核驳回

## 1. 变更背景

微信小程序按**个人开发者（个人主体）**提交审核被驳回：现有「邀请家人」功能被判为「社交属性」，个人主体不允许发布。

审查只看功能形态，不看现实关系。被判社交的触发点是三个：

1. `open-type="share"` 微信转发邀请卡片 → 走微信关系链传播
2. 「复制邀请链接」→ 生成可传播的邀请链接
3. 邀请对象含「保姆阿姨」等非家庭成员 → 「外部关系链」印象

## 2. 变更结论（用户已确认方向）

| # | 决策 | 内容 |
|---|---|---|
| 1 | 方案 | **D：加入码 + 当面扫码**（加入方扫管理员屏幕上的二维码） |
| 2 | 码的形态 | **单一码**，扫码后加入时选身份，身份三选一：家长 / 祖辈 / 阿姨 |
| 3 | 数据 | **不做处理**，数据模型不变、现有 caregiver（阿姨）成员保留，只改产品形态 |

## 3. 变更前后对比

| 维度 | 变更前 | 变更后 |
|---|---|---|
| 管理员入口 | 选邀请类型 → 生成微信分享卡片 / 复制邀请链接 | 生成单个「家庭加入码」（二维码 + 6 位数字） |
| 传播方式 | 微信转发、链接传播 | **当面展示 + 应用内扫码 / 手输**，不通过微信转发、不复制链接 |
| 身份选择 | 管理员生成邀请时预选类型（家长/祖辈/阿姨），绑定进 token | **加入方扫码后自行选身份** |
| 管理员权限 | 家长邀请可勾选「是否管理员」 | 家长加入默认普通家长，管理员权限在成员管理里单独授予 |
| token 内容 | 绑定 `family_id`、`invite_type`、`role`、`is_admin`、`expires` | 仅含 `family_id`、`expires`，身份以加入时用户选择 + 后端校验为准 |
| 阿姨 | caregiver 独立邀请类型 | 复用 grandparent 权限，文案显示为「照护人/阿姨」，不显示为「祖辈」 |
| 数据模型 | — | **不变**，无迁移 |

## 4. 新流程

### 管理员侧（家庭页）

```
家庭页 → 「＋ 家人加入码」
  └─ 显示单个二维码 + 6 位数字加入码（可手输）+ 重新生成 / 作废
```

### 加入方侧（≤4 步）

```
首次进入 → 加入家人的家庭 → 输入家庭加入码（扫码 / 手输 6 位，24 小时有效）
  → 选身份（家长 / 祖辈 / 阿姨）→ 选称谓 → 确认加入（显示家庭名称与身份）→ 进入
  ├─ 家长：妈妈/爸爸/其他家长 → 完整四 Tab（默认普通家长）
  ├─ 祖辈：奶奶/爷爷/姥姥/姥爷 → 照护人今日视图（只显示分配给本人的事项）
  └─ 阿姨：阿姨/保姆阿姨/接送阿姨 → 照护人今日视图（文案显示照护人，只显示分配给本人的事项）
```

## 8. 方案收口（2026-11-20 与 CR 对齐）

在「去社交化」基础上，与 CR 侧对齐后方案进一步收口（覆盖上文第 3 节部分口径）：

| # | 收口口径 | 说明 |
|---|---|---|
| 1 | 管理员权限 | 家庭创建者默认管理员；新加入家长默认**非管理员**（能看四 Tab，录入/编辑/成员管理入口按管理员权限显示）；已有管理员可在成员管理单独授予，后端校验 |
| 2 | 加入码有效期 | 加入码与二维码**统一 24 小时有效**（原 7 天 → 24 小时） |
| 3 | 加入确认 | 加入前向用户显示**实际家庭名称 + 所选身份**，确认后才进入（流程 +1 步，≤4 步） |
| 4 | 家庭归属 | 本轮只做**用户归属一个家庭**的使用路径，不增加多家庭加入或往返入口；数据结构不变 |
| 5 | 边界 | 暂不增加家庭容量配额、不增加「关闭加入」入口开关 |
| 6 | 日程范围 | 阿姨今日视图 = **分配给本人**（非全家庭今日安排），需调整现有「全家庭今日安排」的展示逻辑 |

### 8.1 待确认：祖辈日程范围口径

当前祖辈与阿姨都存为 grandparent，称谓可自定义，不能用称谓里的「阿姨」二字判权限。需明确祖辈今日视图范围：

- **方案 A（推荐）**：祖辈与阿姨一致，都只看「分配给本人」的事项 → 继续复用 grandparent 角色，无需额外区分身份。
- **方案 B**：祖辈看全家庭今日安排、阿姨只看分配给本人 → 两者范围不同，需补充稳定区分身份的设计。

> 本节保留方案收口过程中的历史待确认记录；最终选择见第 9 节。

## 9. 实现确认（2026-11-20）

用户已明确指示“按照设计方案实现”，本次以以下口径作为实现基线：

- 采用 **方案 A**：祖辈与阿姨统一复用 `grandparent`，只查看和执行分配给本人的事项；不按称谓字符串区分权限。
- 普通家长进入四 Tab，可查看家庭安排、参与打卡；默认无日程/任务录入编辑及成员管理权限，管理员可后续单独授予管理员权限。
- 加入码与二维码统一 24 小时有效，四步内完成实际家庭名称与身份确认；本轮只提供单家庭创建/加入/使用路径。
- 保留既有数据模型、caregiver 成员及历史记录，不做迁移、清理或多家庭历史数据截断。
- 普通二维码、应用内扫码与现有 Redis 活动登记按技术方案执行；不增加审批状态机、容量配额、关闭加入开关或多家庭新增入口。
