# ifami 技术方案设计 v0.1

> 对应 [PRD-v0.1.md](PRD-v0.1.md)、[V1-需求列表.md](V1-需求列表.md)、[V1-信息架构.md](V1-信息架构.md)。
> 目标：微信小程序 + Go 后端 + 火山引擎基础设施；前后端分离；具备支撑百万用户的横向扩展与分布式部署能力；同时保持 Phase 0 的建设成本克制。
>
> **执行口径：Phase 0 按最小落地方案推进，完整部署步骤见 [部署方案.md](部署方案.md)；本文档其余章节为目标架构与演进方向（各简化点的恢复时机在 §10）。**
>
> **主体降级（Phase 0 纯个人）**：§2/§4/§5 中的服务号、短信、`getPhoneNumber`、unionid 均为**目标态**（升个体工商户后启用）。Phase 0 用 openid + 小程序一次性订阅消息、无短信，`Channel` 接口只实现 `wechat_subscribe`。恢复点见 [ADR-002](../wiki/architecture/adr-002-notification-receipt.md)。

## 0. 设计目标与约束

| 维度 | 目标 |
|---|---|
| 规模 | 100 万注册用户（≈25–30 万家庭），DAU 15–20 万 |
| 峰值特征 | 触达消息集中在接送时段（07:00–08:30 / 15:30–18:30），约 30% 消息集中在 1 小时内 |
| 可用性 | 触达链路可用性 ≥99.9%（接娃提醒漏发是事故） |
| 演进 | Phase 0 模块化单体 → Phase 1/2 按需拆微服务，数据模型 Day 1 就带分片键 |
| 合规 | 未成年人个人信息保护、等保、UGC 内容安全（打卡照片） |

## 2. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 小程序 | **原生小程序**（非 Taro） | 单平台目标，原生包体积小、能力全（`getPhoneNumber`、`chooseMessageFile`、订阅消息）；主包（今日/日历/打卡）+ 分包（家庭/时间线/周报） |
| 服务号 H5 | 轻量页面（周报落地、邀请落地） | 与小程序共用后端 API |
| HTTP 框架 | **Hertz**（CloudWeGo） | 字节系开源，性能与生态契合 |
| RPC 框架 | **Kitex**（拆微服务时启用） | Phase 0 不用，模块边界按 Kitex IDL 预留 |
| ORM | GORM（谨慎用关联，显式 SQL 做复杂查询） | — |
| 数据库 | 火山引擎 **RDS MySQL**（跨 AZ 主备） | 百万用户量级单主+只读副本足够，分片方案预留（见 §6） |
| 缓存 | 火山引擎 **Redis** | 会话、access_token 集中管理、日程热数据、分布式锁 |
| 消息队列 | 火山引擎 **BMQ/RocketMQ** | 打卡事件流、触达任务、延迟消息（升级策略核心依赖） |
| 对象存储 | **TOS** + CDN | 打卡照片；防盗链签名 URL。课表识别原图 Phase 0 落本地临时目录、识别后即删（§5.5.2） |
| AI 能力 | **火山方舟·豆包多模态大模型** | 课表拍照识别（图→结构化 JSON）、自然语言速记解析 |
| 短信 | 火山引擎**短信服务** | 教育类签名报备需 2–4 周，最早启动 |
| 可观测 | TLS 日志 + APMPlus + 云监控告警 | 触达看板建在指标之上（§8） |
| CI/CD | 代码仓 → 镜像仓库 CR → VKE 滚动发布 | dev / staging / prod 三环境 |

## 3. 服务拆分（模块化单体起步，边界按微服务预留）

Phase 0 部署为**同一二进制、两个进程**（`ifami serve api` / `ifami serve worker`），跑在 1 台 ECS 的 systemd 上（本机原生，无 Docker）——不用 VKE、不用 MQ（延迟任务由 Worker 轮询 `notify_jobs.next_check_at` 替代延迟消息）。内部模块边界就是未来的服务边界：

| 模块 | 职责 | 拆分时机 |
|---|---|---|
| identity | 微信登录、unionid 合并、手机号、成员/角色/权限 | 不拆（共享度高）或最后拆 |
| schedule | 日程/重复规则/冲突检测/管理视图 | 第一个拆（读多，可独立扩） |
| task | 打卡任务/提交/月历统计 | 第二个拆 |
| notify | 触达引擎：路由、升级、通道适配、回执 | 独立 Worker 起步即分离（可用性隔离） |
| growth | 时间线、周报生成 | Phase 1 拆 |
| ingest | 课表识别/NL 解析（调用方舟） | Phase 1 拆（资源特征不同，独立伸缩） |

模块间 Day 1 只通过**接口 + MQ 事件**通信，禁止跨模块直连表——这是"能拆"的唯一保证。

## 4. 核心数据模型

所有业务表带 `family_id`，用户维度表带 `user_id`——两个分片键 Day 1 就位。

```sql
users(user_id PK, unionid UNIQUE, phone_enc, nick, avatar, created_at)
identities(id PK, user_id FK, channel[miniapp|offiaccount|app], appid, openid, UNIQUE(channel,appid,openid))
families(family_id PK, name, creator_id, settings JSON)          -- settings 预留家庭配置
members(member_id PK, family_id FK, user_id NULL, type[real|virtual],
        role[admin|parent|grandparent|child], relation_label, phone_enc NULL,
        status, invited_by, UNIQUE(family_id, user_id))
children 即 members(type=virtual, role=child)，档案归属 member_id（而非家庭）

schedules(schedule_id PK, family_id, child_member_id, title, type[course|pickup|activity|reminder|school],
          rrule, start_time, end_time, location, note, owner_member_id, status)   -- school 可无责任人
ingest_jobs(job_id PK, family_id, creator_user_id, status, images JSON, result_enc,
          stats JSON, error_code, heartbeat_at, created_at, finished_at)     -- 拍照导入任务（见 §5.5）
schedule_instances(instance_id PK, schedule_id, family_id, occur_date, start_at,
          owner_member_id, status[active|cancelled|done])           -- 重复规则物化（见 §5.3）
tasks(task_id PK, family_id, child_member_id, name, goal_type[photo|timer|count],
          goal_value, freq, owner_member_id, status)
checkins(checkin_id PK, task_id, family_id, child_member_id, submit_member_id,
          payload JSON, media_tos_key NULL, created_at)             -- 事件流源头
notify_jobs(job_id PK, family_id, target_user_id, level[strong|medium|weak],
          channel_state JSON, payload, status, created_at)          -- 触达状态机（见 §5.2）
events_stream(id PK, family_id, type[checkin_done|streak|goal_hit|schedule_done], ref_id, created_at)
          -- 千人千面激励的预留钩子，V1 只写不消费
```

手机号等敏感字段**字段级加密**（KMS 托管密钥），展示层脱敏。

## 5. 关键链路设计

### 5.1 登录与账号合并

```
小程序 wx.login → code → 后端 code2session → openid + unionid
  ├─ unionid 已存在 → 下发会话
  └─ 不存在 → 创建 user（虚拟成员转正同样走这个钩子：members.user_id NULL → 绑定）
getPhoneNumber → 后端用 session_key 换手机号（按次计费）→ 加密入库
```

- 会话：采用「进程内本地缓存 → Redis → MySQL 兜底」多级存储（7 天过期），Header 带 `family-id` 表示当前家庭上下文。
- **权限中间件**：每个请求校验 `(user_id, family_id)` 的 membership 与角色——日程/任务写操作仅允许管理员。
- access_token（小程序/服务号）集中由 identity 模块管理并缓存，全系统单点取用，避免互相顶掉。

#### 5.1.1 会话多级存储与 Redis 弱依赖

Phase 0 单 ECS 内存较小，Redis 可能因内存不足无法启动；Redis 在本阶段定位为缓存/会话加速层，不应阻断微信登录。因此会话存储采用方案 C：

```text
L1：api 进程内本地内存 cache
L2：Redis（可用时作为共享缓存）
L3：MySQL auth_sessions 兜底表
```

写入会话：登录成功后先写 L1，再 best-effort 写 Redis；Redis 写失败只记录 warning，不阻断；最后写 MySQL `auth_sessions` 作为可靠兜底。只有 MySQL 写失败才判定登录失败。

读取会话：鉴权先查 L1；未命中查 Redis；Redis 命中则回填 L1；Redis 不通或未命中时查 MySQL；MySQL 命中后回填 L1，并 best-effort 回写 Redis。三层都未命中才返回未登录。

MySQL 兜底表由迁移 `0011_create_auth_sessions.up.sql` 创建：

```sql
CREATE TABLE auth_sessions (
  token      VARCHAR(128) NOT NULL PRIMARY KEY,
  user_id    BIGINT UNSIGNED NOT NULL,
  expires_at DATETIME NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_expires_at (expires_at),
  KEY idx_user_expires (user_id, expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

边界：Phase 0 单 api 进程下，L1 只做加速，进程重启丢失可接受；重启后会从 Redis/MySQL 回填。未来多实例时，Redis/MySQL 仍是跨进程共享来源，L1 继续作为短期加速层。

### 5.2 触达引擎（本系统最核心工程）

**关键实现事实：微信模板消息无已读回执。** 因此需求 R4.3 的"未读"实现为**确认回执制**：

```
日程临近(可配置提前量) → 生成 notify_job(level=strong)
  → 通道1: 服务号模板消息（带小程序跳转页）
  → 用户点开小程序对应页 = 回执（T+0 上报）
  → 15min 无回执 → 通道2: 短信
  → 30min 无回执 → 通道3: 通知备份联系人（配偶）
弱触达不推；中触达仅服务号。
```

- 状态机与计时：Phase 0 用 `notify_jobs` 表的 `next_check_at` 字段 + Worker 轮询（每 30s 扫一次到期任务）；Phase 1 起切换为 **MQ 延迟消息**（发通道 1 时同时投递 15min/30min 延迟检查消息，回执到达即取消）。
- **微信侧配额管理**：模板消息有日额度与 QPS 限制，notify 模块内置配额计数与令牌桶，高峰排队匀速发出；额度需提前向微信申请提升。
- 通道适配层抽象 `Channel` 接口（微信模板/订阅消息/短信/App push），App push（V2）只是新增一个 Channel 实现。
- 祖辈的默认路由：`strong = [服务号, 短信兜底]`，由角色默认值决定，可在成员设置覆盖。

### 5.3 重复日程展开与冲突检测

- 存储 RRULE 模板，**物化未来 90 天** `schedule_instances`（后台每日滚动续展）。查询、提醒、冲突全部打在实例表上——避免每次请求展开 RRULE。
- 冲突检测 = 同 `child_member_id` 或同 `owner_member_id` 的实例时间重叠查询（实例表上有索引），创建/修改时同步返回，允许强制保存。
- 接送高峰查询集中在 `occur_date + family_id`，`(family_id, occur_date)` 索引即可支撑。

### 5.4 打卡事件流（激励钩子）

`checkins` 写入后投递 MQ 事件到 `events_stream`。V1 消费者只有一个：时间线/周报聚合。激励中台（V2）作为新消费者接入，**零改造接入历史数据**。打卡照片先过微信 `mediaCheckAsync` 内容安全检测，再写 TOS。

### 5.5 拍照导入日程（AI 录入，需求 R2.6）

替代原「复制上一周」模板化录入，作为新家庭初始化录入的主路径。入口仅「＋」动作面板第 3 项「拍照导入日程」，仅管理员可用。

#### 5.5.1 链路

```
小程序 wx.chooseMedia（拍照/相册，≤9 张，compressed）→ 每张标孩子
  → POST 上传 → ingest 写本地临时目录 INGEST_DIR/{family_id}/{job_id}/{seq}.jpg
  → start：API 进程内 goroutine 逐张读图 → base64 → 火山方舟·豆包多模态
  → 服务端归一化为草稿（确定性规则）→ 结果加密写 ingest_jobs.result_enc
  → 任务终态（done/failed）立即删除 job 图片目录
  → 小程序 2s 轮询拿草稿 → 确认屏本地编辑 → confirm
  → ingest 经 ScheduleCreator 接口调 schedule.CreateSchedulesBatch（单事务）→ notify 责任人
Worker（30s）兜底：接管超时/心跳中断任务；清理 >24h 残留图片目录；每日续展重复日程实例
```

#### 5.5.2 图片存储：本地磁盘临时存放，识别后即删

Phase 0 未部署对象存储，原图只在「识别」一步被使用（确认屏缩略图、失败重传用小程序本地临时文件；「对照原图」展示模型返回的 `source_text`），因此不做持久化：

- 抽象 `ingest.ImageStore` 接口（`Put / Get / DeleteJob`），Phase 0 实现 `LocalImageStore`；后续接入 TOS 只换实现，业务代码不变。
- 目录 `INGEST_DIR`（默认 `/var/lib/ifami/ingest`），权限 700、属主为 api/worker 运行用户；api 与 worker 同机，worker 接管任务可直接读取。
- 文件名由服务端生成（`{seq}.jpg`），不使用客户端文件名，防路径穿越；按文件头（magic bytes）校验 JPEG/PNG/WebP；单张 ≤5MB，单任务 ≤9 张。
- 删除时机：任务进入 `done`/`failed` 立即删除整个 job 目录；Worker 每轮清理 mtime >24h 的残留目录（进程异常中断兜底）。
- 不进 MySQL 备份；不打印图片内容与识别原文日志。
- 磁盘占用：单任务 ≤45MB × 并发 ≤2，识别后即删，可忽略。
- 推论：原图不保留，服务端不可重跑已结束任务；失败重试由小程序用本地临时文件重新上传并新建任务。

不选方案：MySQL BLOB（拖大库与每日备份）；Redis（Phase 0 不持久化、占内存）；不落盘同步识别（9 张 1–3 分钟易超时，API 重启无法恢复，无法支持「先去忙」）。

#### 5.5.3 数据表（迁移 `0007_create_ingest_jobs.up.sql`）

```sql
CREATE TABLE ingest_jobs (
  job_id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  family_id       BIGINT UNSIGNED NOT NULL,
  creator_user_id BIGINT UNSIGNED NOT NULL,
  status          VARCHAR(16) NOT NULL COMMENT 'uploading|pending|running|done|failed|confirmed',
  images          JSON NOT NULL COMMENT '[{seq,child_member_id(0=自动识别),status}]，不存路径',
  result_enc      MEDIUMBLOB NULL COMMENT '草稿 JSON，字段级加密（含孩子姓名/原文片段）',
  stats           JSON NULL COMMENT '耗时/草稿数/低置信数/确认数/字段修改数',
  error_code      INT NOT NULL DEFAULT 0,
  heartbeat_at    DATETIME NULL,
  created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  finished_at     DATETIME NULL,
  KEY idx_family_created (family_id, created_at),
  KEY idx_status_heartbeat (status, heartbeat_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

草稿不单独建表：用户编辑在小程序本地完成，确认时整批提交。

#### 5.5.4 接口（`/v1/ingest`，需 `X-Family-Id`，仅管理员）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/ingest/jobs` | 创建任务（`uploading`），返回 `job_id` |
| POST | `/v1/ingest/jobs/:id/images` | multipart 上传单张（`file`、`seq`、`child_member_id`） |
| POST | `/v1/ingest/jobs/:id/start` | 置 `pending` 并异步执行，立即返回 |
| GET | `/v1/ingest/jobs/:id` | 状态 + 进度（done/total）；`done` 时返回草稿 |
| GET | `/v1/ingest/jobs?status=done` | 待确认任务（「先去忙」后回来找结果） |
| POST | `/v1/ingest/jobs/:id/confirm` | 提交最终日程列表 + `force`；返回 schedule_ids 或逐条冲突 |

错误码 6xxx：6001 参数错误、6002 任务不存在、6003 无权限、6004 图片格式/大小不符、6005 识别失败、6006 今日额度用完（每家庭 20 张/天）、6007 状态不允许。Hertz 请求体上限调至 10MB（`server.WithMaxRequestBodySize`）。

#### 5.5.5 识别执行

- 进程内信号量限并发 2；每张图独立调用方舟 Chat Completions（`net/http` 直连，不引 SDK），超时 45s、重试 1 次；执行中每 10s 写 `heartbeat_at`。
- Worker 接管：`pending` 超过 1 分钟或 `running` 心跳中断 >3 分钟的任务重跑一次，再失败置 `failed`。
- 配置新增：`INGEST_DIR`、`ARK_API_KEY`、`ARK_BASE_URL`、`ARK_MODEL`（接入点 ID）。

#### 5.5.6 草稿归一化（服务端确定性规则，必须单测）

1. 校验 `HH:MM` 与结束晚于开始；缺结束时间默认 +60 分钟并标低置信。
2. `school_timetable` 同一上学日组合并为一条「在校」块（type=`school`，最早上课–最晚放学），逐节明细放 `merged_items` 供「展开逐节」。
3. 每个「在校」块按放学时间生成「接 X 放学」接送草稿，责任人待指派。
4. 孩子匹配：图片指定孩子优先；「自动识别」时以 `child_name` 匹配家庭孩子（经 identity 接口取解密名），失败标待选。
5. 有 `date` → 单次；否则 `FREQ=WEEKLY;BYDAY=..`，有 `until` 带 `UNTIL`。
6. `unreadable` 行原样保留，前端显示「需手动补」。
7. 单任务草稿 ≤50 条（与批量创建上限一致）。

#### 5.5.7 schedule 模块配套改动

| 改动 | 说明 |
|---|---|
| 新增类型 `school`（在校） | 责任人可为 0；不触达；冲突仅按孩子判定；周视图不占时段格，表头下方单行展示 |
| 批量创建同批互检 | 现仅与库内实例比较；补充同批条目两两冲突，冲突项带 `index` 便于前端定位 |
| 实例续展 | Worker 每日为 active 重复日程补齐未来 90 天实例（ADR-003 原定但未实现；学期课表必需） |
| 「每天」修复 | 小程序改发 `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR,SA,SU`，后端不扩 DAILY |

#### 5.5.8 小程序

- `pages/import`：选图 + 标孩子 → 并发 3 路 `wx.uploadFile` → start → 进度页（2s 轮询，上限 90s）；「先去忙」时申请订阅消息授权，识别完成经 notify 发 medium 级提醒。
- `pages/import-confirm`：按图分组；低置信标黄；冲突在本地计算（拉取未来 2 周实例 + 同批草稿）；批量指派面板对冲突成员置灰；有待指派项时确认先弹指派面板。
- `pages/import-edit`：显示 `source_text`、多选星期、开始/结束、持续到、删除本条。
- 删除 `pages/template`（复制上一周）及 `app.json` 注册；`pages/event` 去掉「拍照识别/从微信导入」切换；五处 ＋ 面板第 3 项改指 `import`。
- 识别失败：提示并提供「手动安排一件事」，保留已选图片可重试。

#### 5.5.9 合规与验证

- 隐私协议声明相册/摄像头用途（课表识别）；原图识别后即删；`result_enc` 加密。
- 埋点（`stats`）：识别耗时、草稿数、低置信率、确认率、字段修改率——即线上准确率基线。
- 上线前用 50+ 张真实课表做离线评测（前置事项 §6）。

## 6. 百万用户规模化设计

| 手段 | Day 1 就位的 | 按需启用的 |
|---|---|---|
| 无状态服务 | VKE 多副本 + HPA（按 CPU/QPS 伸缩），跨 AZ 部署 | 多地域单元化（百万 DAU 之后再说） |
| 数据库 | 分片键设计（`family_id`/`user_id`）；RDS 跨 AZ 主备 | 读写分离（只读副本）→ 16 逻辑分库（DRDS/自研路由） |
| 缓存 | Redis：会话、家庭首页聚合、周视图、热点日程 | 本地缓存（Caffeine 类）抗热点 |
| 削峰 | 全部写后动作（事件流、周报、实例续展）走 MQ | 触达高峰弹性扩容 notify Worker |
| 外部依赖 | 微信 API 令牌桶、配额计数、失败重试与降级 | 多服务号分流（单号额度见底时） |

容量估算：触达消息日均 ~50 万条，高峰小时 ~15 万条 ≈ 40 QPS 出向——瓶颈不在机器，在**微信侧配额**，所以配额管理比扩容更早做。

## 7. 安全与合规

- 传输全 HTTPS；敏感字段（手机号、孩子姓名）字段级加密；接口展示默认脱敏。
- 未成年人：孩子无独立账号，数据操作均有监护人 membership 鉴权；支持导出与删除（个保法）。
- UGC：打卡照片/评论过微信内容安全 API；家庭间默认零可达（无陌生人入口）。
- 等保二级备案；审计日志（成员变更、权限变更、数据导出）入 TLS 留存 ≥6 个月。

## 8. 可观测性（触达看板是 P0）

- 指标：分通道/分级别的**发送成功率、回执率、升级率、端到端时延**；微信配额水位。
- 告警：强触达 5 分钟成功率 <99% 即电话告警值班人。
- 链路：APMPlus trace 贯穿 `schedule → notify_job → 通道 → 回执`。
- 业务看板独立于系统监控，Phase 0 就要上线——Phase 1 朋友验证的过关条件全靠它。

## 9. CI/CD 与环境

- 三环境：dev（VKE 命名空间隔离）/ staging / prod；镜像走 CR，VKE 滚动发布，prod 分批+可回滚。
- 小程序：体验版（内部）→ 灰度（微信支持按比例）→ 全量；版本与后端 API 版本兼容矩阵入仓管理。
- 数据库变更：gh-ost 在线 DDL，禁止锁表变更进 prod。

## 10. 演进路径

| 阶段 | 架构形态 | 对应产品阶段 |
|---|---|---|
| Phase 0 | **1 台 ECS + systemd 本机部署**：单二进制双进程（api+worker）+ 本机 MySQL/Redis/Caddy（无 Docker）；无 MQ/VKE | 自己家 dogfood |
