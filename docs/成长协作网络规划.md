# ifami 成长协作网络规划（2026-11-01）

> 本文承接 PRD v0.1 与 V1 需求列表，记录当前阶段对产品扩展方向的判断：ifami 不扩成泛家庭生活操作系统，而是沿着「围绕孩子成长的家庭协作网络」演进。

## 1. 核心判断

ifami 的最优长期方向是：**以孩子成长为中心，把家庭内部协作工具，逐步演进为可信熟人家庭之间的成长协作网络**。

不优先做泛家庭生活操作系统，原因是：

1. **当前产品的真实高频场景已经围绕孩子展开**：日程分工、接送、打卡、提醒、成长记录都不是泛生活需求，而是 4–10 岁孩子成长阶段的家庭协作需求。
2. **家庭生活泛场景太宽，容易失焦**：买菜、旅游、账单、家务、老人健康等需求都成立，但它们分别已有强对手或低频弱协同，很难自然承接当前用户心智。
3. **孩子成长天然具备协作网络潜力**：同班同小区、同机构、同年龄段家庭之间有资料、经验、拼课、活动、路线安排等真实熟人协作需求，但必须在家庭工具留存成立后再开放。
4. **私密、反焦虑、无排名是可持续差异**：不做开放广场和跨家庭排名，能避免亲子产品常见的焦虑放大和合规风险。

一句话定位可演进为：**孩子成长家庭协作空间：先让一家人把接送、课表、打卡、提醒协作起来，再让可信家庭小圈子低压力地共享成长经验与资源。**

## 2. 演进原则

### 2.1 坚持的边界

- 默认私密：孩子数据、家庭协作记录默认只在家庭内可见。
- 不做开放广场：任何跨家庭能力都必须是邀请制、熟人制、小圈子制。
- 不做排名打榜：不做孩子/家庭之间的成绩、坚持天数、成长值排名。
- 不替家庭教育孩子：打卡与记录只做工具，不替家长选择激励手段。
- 不做独立 IM：聊天继续在微信里，ifami 只承载挂在日程/打卡/记录上的上下文沟通。
- 不直接跳旅游交易平台：出游可以作为家庭活动/成长记录/圈内经验，但不做 OTA 或交易撮合起步。

### 2.2 判断新增功能的标准

新增功能必须至少满足以下两条：

1. 能提高家庭内部协作频率或完成率；
2. 能自动沉淀孩子成长记录，而不是制造额外整理负担；
3. 能自然形成可分享但不焦虑的家庭成果；
4. 能为未来熟人家庭小圈子积累结构化素材；
5. 不破坏私密、无排名、无陌生人社交的红线。

## 3. 分层路线

### L1：家庭协作工具层（当前 V1 基本盘）

目标：让一个家庭真的用起来，解决「今天谁做什么、有没有按时完成」的问题。

核心能力：

- 家庭与成员：家庭账户、邀请成员、多孩、管理员权限；
- 日程分工：课程、接送、活动、提醒、责任人、冲突检测；
- 今日/周视图：祖辈能一眼看懂今天要做什么，父母能看一周安排；
- 打卡记录：阅读、跳绳、练琴等任务创建、提醒、提交；
- 触达中枢：订阅消息、点击回执、红点、升级通知。

成功信号：每周仍有家庭主动录入/查看/打卡，祖辈减少反复电话确认，强触达能被确认。

### L2：成长记录与成果感层（V1.5 / V2）

目标：让协作结果自然变成「看得见的成长」，提升留存和家庭内传播。

核心能力：

- 成长时间线：日程完成、打卡、照片、里程碑自动沉淀；
- 家庭周报：每周自动总结孩子本周坚持、活动、照片与提醒完成情况；
- 低压力分享：周报/里程碑可转发微信，但不带排名、对比、PK；
- 管理视图：主理人能看到全部重复日程和打卡任务，降低长期维护成本；
- 拍照导入日程：拍现成课表识别成重复日程，让初始化与维护成本显著下降。打卡侧保留独立「任务模板」能力，避免和日程导入混用入口。

成功信号：用户愿意回看、转发周报，连续 4 周家庭仍有协作行为，模板显著提升首周录入完成率。

### L3：熟人家庭小圈子层（V3）

目标：在已有家庭留存和成长资料的基础上，让 3–10 个熟人家庭形成低压力协作网络。

核心能力：

- 邀请制家庭圈：同班、同小区、同机构家庭之间建立小圈；
- 圈内资料库：课程通知、机构资料、活动攻略、成长经验结构化沉淀；
- 圈内活动：非交易化的拼课、约活动、亲子出游计划协作；
- 可控互见：只共享用户主动选择的周报片段、资料或活动，不开放孩子全量档案；
- 反焦虑机制：无排名、无打榜、无公开推荐流，圈内内容以资料/活动/经验为主。

成功信号：一个家庭邀请另一个家庭加入，圈内资料被复用，活动/课程协作带来新家庭增长。

## 4. 当前优先级结论

当前不应扩展的方向：

- 泛旅游：可作为「家庭活动」和「成长记录」的内容类型，但不做交易、攻略平台、酒店机票路线规划；
- 泛家庭圈：不做开放社区，不做陌生家庭匹配；
- 泛生活管家：不做买菜、家务、账单、维修等宽泛家庭事务；
- 泛教育社区：不做升学焦虑内容、不做机构营销、不做成绩排名。

当前应优先推进的方向：

1. **拍照导入日程**：先解决初始化与重复维护成本，提升持续使用；
2. **执行端变更反馈闭环**：先解决祖辈/执行人不能编辑但要表达「去不了/要调整」的问题；
3. **成长时间线自动沉淀**：把协作行为转成长期价值；
4. **家庭周报**：把长期价值包装成家庭内传播与未来圈子分享的素材。

这四项共同构成从 L1 到 L2 的最小跃迁：**更容易录入 → 更可靠执行 → 自动留下记录 → 每周形成成果感**。

## 5. P0 产品设计方案

以下 P0 是「下一阶段产品 P0」，不是推翻当前 V1 基础 P0。它们用于把当前可用工具推进到可留存、可验证、可外扩的状态。

### P0-1 拍照导入日程（替代原「模板化录入」）

对应需求：R2.6、R3.1（R2.5 复制上一周已废弃，R2.7 微信导入不做）。

#### 要解决的问题

家长维护一周课表和多个打卡任务成本高。原「复制上一周」依赖已有数据，新家庭首周无从复制，且复制产物为单次日程，不能解决初始化录入。家长手里通常已有现成课表（机构课表、学校作息、群通知截图），直接拍照识别成重复日程，一次录入、以后每周自动出现。

#### 入口设计

- 「＋」动作面板第 3 位「📷 拍照导入日程」，**唯一入口**；
- 打卡页保留独立「任务模板」入口，与日程导入不混用。

#### 核心流程

1. 管理员拍照或从相册选图（≤9 张），每张标孩子或「自动识别」；
2. AI 识别，可「先去忙」，完成后提醒；
3. 草稿确认屏按图分组：低置信标黄、冲突就地标出、无法辨认行可手补；学校作息合并为「在校」块并自动生成接放学；
4. 批量指派责任人，必要时单条对照原文修改；
5. 确认后一次入库，进入今日/周视图与提醒链路。

#### 验收标准

- 3 张图到出草稿 ≤60 秒；首次家庭初始化（课外班 + 学校 + 接送）≤5 分钟；
- 所有识别内容先以草稿呈现，不能静默入库；
- 批量启用 5 个打卡模板 ≤30 秒；
- 非管理员不可进入导入链路；原图识别后即删。

#### 埋点

- 导入入口点击率、识别成功率、识别耗时；
- 草稿确认率、字段修改率（准确率基线）；
- 首次家庭组建后 24 小时内日程/任务创建数；
- 导入日程 7 天内被查看/提醒的比例。

### P0-2 执行端变更反馈闭环

对应需求：R2.10、R4.3、R6.1。

#### 要解决的问题

V1 已收紧为仅管理员可录入编辑，但祖辈/执行人真实场景里会遇到「今天去不了」「时间改了」「地点不清楚」。他们不能编辑日程，但必须能低成本发起反馈，否则协作仍会回到微信群。

#### 入口设计

- 今日视图日程卡片增加「要调整」按钮；
- 日程详情页增加「无法执行 / 需要调整」反馈入口；
- 强触达通知落地页可直接进入该日程详情；
- 管理员端出现待处理红点和「待处理调整」列表。

#### 核心流程

1. 执行人点击「要调整」；
2. 选择原因：去不了、时间不对、地点不清楚、需要换人、其他；
3. 可补一句说明；
4. 系统强触达管理员或责任家长；
5. 管理员进入待处理项，选择改时间、换责任人、取消本次、标记已处理；
6. 处理结果回传给原执行人，并更新日程实例。

#### 验收标准

- 非管理员可以发起反馈，但不能直接修改日程；
- 管理员收到反馈后必须能在 2 步内进入处理；
- 每个反馈有状态：待处理、已处理、已忽略；
- 处理动作必须写入事件流，供成长时间线/周报判断协作完成情况；
- 反馈通知属于强触达，需遵守免打扰和升级策略。

#### 埋点

- 反馈发起率；
- 反馈原因分布；
- 管理员处理时长；
- 反馈后是否仍发生人工微信沟通（Phase 1 访谈验证）。

### P0-3 成长时间线自动沉淀

对应需求：R5.1。

#### 要解决的问题

如果 ifami 只解决当天协作，很容易被当成临时工具；需要把日程、打卡、照片、里程碑自动沉淀为孩子成长记录，让家庭看到长期价值。

#### 入口设计

- 孩子详情页增加「成长时间线」；
- 打卡成功页提示「已记录到成长时间线」；
- 日程完成/活动结束后可补一张照片或一句记录；
- 家庭页孩子卡片展示最近一条成长记录。

#### 核心流程

1. 系统从事件流自动生成候选记录：打卡完成、连续事实、活动日程、照片提交；
2. 按孩子归档，默认家庭内可见；
3. 管理员可隐藏、删除、补充说明；
4. 时间线按月份组织，支持孩子筛选；
5. 周报从时间线中抽取本周摘要。

#### 验收标准

- 无需用户手动整理即可生成基础时间线；
- 时间线不出现排名、分数、打榜式视觉；
- 涉及照片/评论的 UGC 必须先过内容安全检查；
- 支持按孩子筛选；
- 支持删除单条记录，后续补齐孩子数据导出/删除能力。

#### 埋点

- 时间线访问率；
- 自动记录生成数；
- 用户手动补充/删除比例；
- 时间线访问后次周留存变化。

### P0-4 家庭周报

对应需求：R5.2、R4.2。

#### 要解决的问题

家庭需要阶段性成果感，否则协作工具容易变成负担。周报把一周安排、打卡、照片和里程碑整理成低压力总结，也是未来熟人家庭圈的分享素材。

#### 入口设计

- 打卡页或家庭页增加「本周小结」入口；
- 每周固定时间通过中等级触达提醒管理员查看；
- 周报页提供「转发给家人」；
- 后续 V3 仅允许用户主动选择片段分享到家庭圈。

#### 内容结构

1. 本周概览：完成了哪些日程/打卡；
2. 孩子片段：按孩子展示 1–3 条代表性记录；
3. 坚持事实：连续天数、完成次数，只做事实，不做勋章；
4. 协作提醒：下周未安排责任人的事项、待处理反馈；
5. 家庭照片/里程碑：来自时间线的精选项。

#### 验收标准

- 周报自动生成，用户不需要手工编辑才能查看；
- 周报可转发微信，但分享卡不出现排名、PK、超过多少家庭等文案；
- 订阅消息提醒属于中等级触达；
- 未生成足够数据时展示空状态，引导去录入模板，而不是生成虚假总结；
- 周报可按孩子查看，默认只对家庭成员可见。

#### 埋点

- 周报生成率；
- 周报打开率；
- 周报转发率；
- 周报打开后 7 天内新增日程/打卡任务数；
- 周报对 4 周留存的影响。

## 6. 建议实施顺序

### 第一批：先做拍照导入日程 + 反馈闭环

原因：它们直接影响家庭协作闭环是否成立。

- 拍照导入降低初始化与每周维护成本；
- 反馈闭环补上「非管理员不能编辑」后的执行端表达能力；
- 两者都能直接进入 Phase 1 验证指标。

### 第二批：再做成长时间线 + 家庭周报

原因：它们依赖事件流和足够行为数据，适合在基础协作行为跑起来后做。

- 时间线先自动沉淀，不追求复杂编辑；
- 周报先做小程序内查看和微信转发，不做公开分享；
- 为 V3 家庭圈预留「主动选择片段分享」能力。

下一步进入原型和需求细化时，建议按以下顺序更新：

1. `prototype/index.html`：补齐拍照导入日程、反馈入口、时间线、周报的可点击原型；
2. `docs/V1-需求列表.md`：把下一阶段 P0 的验收标准合并到对应 R2/R3/R5/R6；
3. `docs/V1-信息架构.md`：补充时间线、周报、待处理反馈入口；
4. `docs/技术方案设计.md`：补事件流、反馈状态、周报生成任务与内容安全检查链路；
5. 等产品 check 后再进入实现代码。

## 8. 暂不处理的问题

- 家庭圈具体权限模型：等 L2 数据和分享行为验证后再设计；
- 旅游/亲子活动交易：只作为活动日程和成长记录内容，不进入交易闭环；
- 激励体系：继续后置，只保留事件钩子；
- App：父母侧 push 需求被验证后再评估；
- 服务号/短信：升个体工商户后恢复目标态触达方案。
