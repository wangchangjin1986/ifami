## 2. 技术方案与当前缺口

现有身份模块使用无状态 HMAC 邀请 token，里面绑定 invite_type/role/is_admin；家庭页通过微信分享或复制路径传播；加入接口同时兑换微信 code 和写成员。现有照护人页读取整个家庭的实例列表，后端完成/反馈仅校验家庭成员身份。

推荐保留 **普通二维码 + 应用内 wx.scanCode + 现有 Redis 登记**：

- 纯签名不能完成全局六位码查找与单码作废；MySQL登记需要改表，本轮不选。
- Redis保存24小时活动凭据与少量管理操作回执，复用现有go-redis，不新增服务或业务表。
- 签名业务声明仅含 family_id、expires；身份和管理员权限不进入签名。
- 码属于家庭；管理员在生成、读取、换码、作废时必须通过服务端实际 membership 鉴权。
- Redis不可用时码管理和新加入暂不可用；已有成员登录和协作保留现有会话兜底。不能用各进程内存或仅签名校验绕过作废。

普通二维码协议建议：

```text
IFAMI_JOIN_V1:<六位数字>:<generation_id>:<签名凭据>
```

数字使用 crypto/rand 生成，范围000000–999999，保持前导零。generation_id为至少128位随机代际标识，是二维码协议字段，不是身份/权限声明；数字码与二维码关联同一登记。二维码本地canvas绘制，不调用第三方在线生成服务。应用内扫码限制普通QR并使用相机；不解析外部网址或自动跳转。取消扫码返回手输入口。

本轮采用普通二维码；最终审核效果仍以新体验包提审为准。

## 3. 加入码生命周期（精简）

### 3.1 Redis记录

| 记录 | 用途 |
|---|---|
| 家庭当前码 | family_id、generation_id、签发者审计信息、expires_at、可供管理员读回的码与二维码材料 |
| 数字码索引 | 六位码的密钥HMAC摘要 → 家庭当前登记；所有活动家庭之间不能重码 |
| 管理操作回执 | actor_user_id/family_id/Idempotency-Key → 已执行的码管理版本，建议30分钟去重 |
| 基础访问保护计数 | 限制错误码试探，不是家庭人数或换码使用配额 |

管理员读回所需原码建议复用 FieldCipher 加密存储；日志不记录数字码、签名或二维码原文。没有 join_attempt、审批队列、确认结果缓存或受理状态机。

### 3.2 生成、换码与作废

1. 打开面板先读当前码；读取不换码、不续期。没有有效码时生成，24小时从成功生成的服务端时间起计算。
2. 使用Redis Lua原子检查候选数字无活动碰撞，写入新登记并替换家庭指针。随机碰撞重抽；失败保留旧码，不先删后建。
3. 主动重生成更换数字与generation，旧数字/二维码登记随之失效。重生成请求带Idempotency-Key，网络重试不反复换码；旧操作回执对应的代已被替换时，读当前码，不能重新激活历史代。
4. 作废带期望generation，避免旧面板删除他人刚生成的新码；重复作废同一代视为成功。TTL负责清理，服务端expires负责拒绝；到期边界采用 now >= expires。
5. Redis活动登记TTL、签名expires及页面“24小时有效”统一，禁止单独保留七天签名、滑动续期或靠手机时间授权。
6. 成功加入不消耗码，同一家庭24小时内可以有多个家人分别加入；“一个人一个家庭”不等于“一个家庭只有一名成员”。

本轮没有七天冷却机制。换码不立即选回刚被替换的数字；未来数字仍可能复用。扫码还必须匹配generation与签名，旧二维码不能因数字复用变有效；手输有效旧数字可能指向别的家庭，因此必须显示实际家庭名称并由用户确认，不能自动加入。

码归家庭，签发者撤权不自动改变码生命周期；作废、重生成、到期或登记丢失才撤销。移除知晓码的人时，管理员可作废/重生成码。这是初稿保留的技术建议，未额外增加成员撤权与Redis的联动依赖。

Redis清空后旧凭据不能凭签名复活。码管理请求超时按结果未知处理，重试同一操作key或读取当前代，不提前显示“作废成功”。作废以服务端最终验证码时序为界：作废之后校验旧码的加入拒绝；在作废之前已通过最终校验、正在提交的请求可能完成，不引入分布式事务追回在途请求。

## 4. 接口契约与直接加入

### 4.1 码管理与加入接口

| 接口 | 权限 | 行为 |
|---|---|---|
| GET /v1/families/:fid/join-code | 目标家庭active管理员 | 当前码或has_code=false，不自动续期 |
| POST /v1/families/:fid/join-code | 目标家庭active管理员 | 生成/重生成，操作幂等 |
| DELETE /v1/families/:fid/join-code | 目标家庭active管理员 | 按generation作废 |
| POST /v1/family-join/preview | 微信会话用户 | 检查活动码，返回实际家庭名称、generation、签名与expires，不写成员 |
| POST /v1/family-join/confirm | 微信会话用户 | 重验码、身份与称谓后直接写成员，返回真实成员身份 |

加入码放body，避免进入URL日志。码管理路径fid与家庭请求头应一致；preview/confirm不从X-Family-Id获取目标，也不要求用户已经是目标家庭成员。目标由活动码解析。无需新增页面或管理员审批接口。

码管理结果示例：

```json
{
  "join_code": "482913",
  "generation_id": "opaque-generation",
  "qr_content": "IFAMI_JOIN_V1:482913:opaque-generation:<signed-family-and-expiry>",
  "expires_at": "2026-11-21T06:00:00Z"
}
```

preview手输入参为join_code，扫码额外传generation_id、credential；返回family_id、**实际family_name**、generation_id、credential、expires_at。家庭名直接来自服务端families.name，不从URL/缓存/用户输入猜测；不附带孩子名、成员列表或日程。

confirm示例：

```json
{
  "join_code": "482913",
  "generation_id": "opaque-generation",
  "credential": "<signed-family-and-expiry>",
  "identity": "caregiver",
  "relation_label": "接送阿姨"
}
```

手输通过preview取得相同凭据后再confirm。**不再使用join_attempt_id。** preview之后码改变、过期或实际家庭变化，confirm拒绝，用户重新核对家庭；不静默改投别的家庭。家庭名称是确认信息，权限仍取活动码与membership。

返回family_id、member_id、role、is_admin、relation_label、already_member。复用已有用户会话，不在成员入库之后创建新会话。错误区分码不可用、扫码内容错误、参数错误、已属其他家庭、已被移除需管理员处理、暂不可用和旧客户端更新；码无效/过期/作废对加入方统一提示，让家人重新展示。

### 4.2 身份映射

| 选择 | 持久化role | 新加入is_admin | 路径 |
|---|---|---|---|
| parent | parent | false | 查看四Tab，无录入/编辑/成员管理入口 |
| grandparent | grandparent | false | 照护人今日；仅本人分工 |
| caregiver | grandparent | false | 照护人今日；仅本人分工 |

只允许三种identity与对应称谓预设；拒绝用role/is_admin/user_id/family_id入参授予权限。称谓用于展示，不用它判断阿姨身份或访问范围。管理员权限仍由已有成员管理接口单独授予，后端RequireActive已返回effectivePermissionRole，可继续识别独立is_admin标记。

### 4.3 幂等、单家庭与并发

- confirm每次都重新查活动登记、generation、签名及24小时有效期；不得只凭preview曾成功就写成员。
- 复用identity的MySQL事务。创建家庭与加入家庭都先锁定当前users行，再检查active memberships，使同一用户同时加入A/B或创建A/加入B也只有一个有效归属；仅有(family_id,user_id)唯一键不足以保证跨家庭单归属。
- 同用户已属目标家庭：返回现有成员实际role/is_admin，不覆盖权限或称谓；无需新增记录。返回前仍完成正常会话与成员校验，已有关系不是新授权。
- 已属其他家庭：拒绝本次加入或再次创建家庭，并明确提示先处理原家庭关系；不自动退出、搬迁或删除数据。
- 无active关系：按普通权限创建真实成员；实际MySQL1062按具体驱动错误识别后回查，不能假设GORM启用了TranslateError。
- 对同目标家庭存在removed记录，本轮不自动恢复、不新建第二条，提示管理员处理；重入授权不在本次新增范围。
- 响应丢失后重复confirm，若码仍有效则回查现有成员；若码已失效，先从/v1/me核对是否已经加入。已经入库的成员保留，未入库不得绕过作废重建。
- 成员创建成功但刷新/me失败，页面提示“已加入，家庭信息刷新失败，可重试”，不能将已保存成员误报为确定未加入。

“用户归属一个家庭”在新创建/加入写入口执行；已有多家庭历史关系不迁移、不截断、不私自挑一个删除。本轮只验收单家庭路径，不增加多家庭切换/加入/往返入口。旧邀请写入口必须一并退出，避免绕过新归属校验。

## 5. 本人分工的后端权限（本次新增影响）

这是阿姨日程范围变化的实现要求，不能只改照护人页面文案或forEach过滤。

### 5.1 A方案统一判定

每次经identity.RequireActive取得真实member_id与effective role：

- admin：家庭日程读取与录入编辑沿用管理员权限。
- parent（非管理员）：可读取家庭安排/查看四Tab并参与打卡；日程/任务创建编辑、导入、成员管理入口隐藏，服务端写接口仍拒绝。
- grandparent（非管理员，A下包含祖辈与阿姨）：只能读取和执行**当前owner_member_id == 自己member_id**的日程实例。

不信客户端owner过滤参数，不按relation_label匹配，不让多个孩子或家庭ID伪造扩大范围。

成员录入也包含添加孩子。现有identity.AddChild允许admin/parent，需按本次普通家长无录入入口的口径收紧为管理员；POST /v1/families/:fid/children必须由后端拒绝普通家长直接调用。“孩子档案不变”指模型和既有档案数据不迁移、不清理，不能解释为保留原录入权限。

### 5.2 查询、详情与操作

| 链路 | 计划限制 |
|---|---|
| GET /v1/schedules/instances | 服务端从membership生成scope；Store查询同时约束family_id/date/owner_member_id，今日与明日预告都过滤 |
| 新GET /v1/schedules/instances/:iid | 验证当前家庭与owner后返回实例；parent/admin按原家庭权限读取 |
| GET /v1/schedules模板列表 | 照护人路径拒绝全模板读取，避免绕过实例过滤获得全家庭安排；父母/管理员保留 |
| POST实例complete/feedback | 照护人必须仍是当前owner；在同一实例事务内锁行并校验再写，避免改派与执行之间的竞态 |
| PATCH/DELETE日程、改分工、导入 | 继续仅管理员；无前端入口也不能省服务端校验 |

列表先过滤再补关联模板展示数据，不能先把全家庭列表发给客户端。参数改成任意日期也只能得到本人分工。实例已改派时，旧照护人不能查看详情、标记完成或提交反馈，新owner可以；done重放也必须先过当前owner检查。

已有`0001`迁移提供`idx_owner_date(owner_member_id, occur_date)`，可支撑本人日期查询；家庭维度也已有日期索引。本轮复用这些索引，详情/操作按实例主键定位，不因增加scope另建表或新增迁移。

CompleteInstanceWithEvent与反馈入库保持事务一致，失败不写事件/通知。现有schedule Store自己拥有实例表，身份仅通过接口提供membership，禁止跨模块JOIN members。

### 5.3 通知与旧详情路径

照护人页红点已按接收人过滤，但旧通知可引用已改派实例，详情目前主要从URL参数展示，因此也要覆盖：

- 新详情页只用instance_id/family上下文向后端取得当前可见实例；URL内title/location/note不能绕过后端scope显示新的数据。
- 日程红点/待发送日程提醒经当前实例scope判断；notify通过消费方定义的可见性接口读取schedule结果，不直接查实例表。保留统一notify路由，不重做通知状态机。
- 解除分工仍可以告诉旧owner“分工已调整”，但对照护人显示最小提示，不附带其他人的当前安排、地点或备注，也不提供可绕过scope的详情。
- 已经发送或被用户看到的历史内容无法撤回；本次限制新查询、操作和后续发送，既有业务记录不批量清理。

方案 B 未采用；当前统一 `grandparent` 的本人 scope 直接适用于祖辈与阿姨。

## 6. 小程序与原型对齐

加入用户路径为四个逻辑步骤，可以同一页面分块展示，沿用已更新原型：

1. 扫码或手输六位码。
2. 选择家长、祖辈、阿姨。
3. 选择对应称谓。
4. 展示服务端实际家庭名称、所选身份/称谓，点击“确认，加入家庭”。

微信技术会话在preview前由现有wx.login/ensureLogin后台建立，不新增“注册/登录/账号”页面或要求取手机号。产品里的微信授权步骤不变成第五个可见表单。

- 保留pages/invite/index注册路径，改为应用内加入页；旧invite_type/is_admin URL不参与新授权。
- 未归属家庭时展示创建/加入入口；已归属家庭时显示实际家庭，不新增加入另一个家庭或混合角色返回入口。
- family页码面板含24小时有效信息、真实二维码、数字、重生成、作废；网络失败或过期不显示占位图为有效码。
- 取消扫码、相机拒绝、非ifami二维码均可回手输。输入使用顶层model:value，前导零保留；改码清理旧preview，改身份同步称谓与确认区。
- 新家长四Tab保持可见，但FAB、安排录入、任务创建/编辑、导入、成员管理等入口按实际is_admin隐藏；服务端同时校验。管理员后来授予权限，刷新/me后按实际权限开放。
- 阿姨今日和明日预告只显示本人日程；A下祖辈一致。本人没有安排显示“今天没有分配给你的事项”，不是“家庭今天没有安排”。
- 成功后刷新/me，再设置返回的family_id，按真实membership落地；不能用选择的identity覆盖已有成员实际权限。
- 移除邀请open-type=share、copyInvite、邀请onShareAppMessage和旧分享菜单；不提供二维码保存/复制链接动作。其他功能分享不携带加入凭据。

原型已同步第4步、24小时、普通家长“查看家庭安排、参与打卡”、当前家庭本人分工样例与动态示例家庭；实现时确认区家庭名必须由preview结果填入，不得把原型示例值写死为真实结果。

## 7. 安全保护与明确不做的扩展

保留基础正确性：安全随机、活动码碰撞重抽、generation匹配、真实会话/成员校验、无录入权限的后端拒绝、错误输入保护、成员唯一性。

六位码熵较低，preview/confirm应共享按真实user_id和可信客户端IP的失败尝试保护；阈值作为实现参数校准，不是家庭人数、每日换码或总码量配额。两条入口不能互相绕过；Redis不可用不放宽加入授权，登录仍走现有兜底。

本轮不增加管理员审批、受理状态机、join_attempt结果登记、家庭人数容量限制、每日换码额度、全局占用阈值、七天冷却、关闭加入开关、地理当面证明、多家庭加入或混合角色往返。
